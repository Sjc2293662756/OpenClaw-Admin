## 1. 目标

明确已从正式产品隐藏但仍保留源码的能力、服务端可达性和清理条件，防止把“菜单不可见”误认为“代码与接口已安全移除”。

## 2. 范围

| 遗留能力 | 正式前端 | 服务端现状 | 处理原则 |
|---|---|---|---|
| Hermes 全部模式 | 无正式路由/菜单 | `/api/hermes*`、`/api/hermes-cli*` 前置返回 `410 ENDPOINT_RETIRED`，内部源码保留 | 当前安全边界已完成，不安排直接删除 |
| 远程终端 | 无正式路由/菜单 | `/api/terminal/*` 前置返回 410，后方进程管理代码不可达 | 当前保留源码，避免直接删除引发共享依赖回归 |
| 远程桌面 | 无正式路由/菜单 | `/api/desktop/*` 前置返回 410，后方会话代码不可达 | 同上 |
| 虚拟公司 | 无正式路由/菜单 | 场景/办公室相关代码部分仍被工坊使用 | 保留共享代码，后期按正式依赖评估 |
| 数据备份 | 无正式路由/菜单 | `/api/backup/*` 前置返回 410；旧任务代码和 `backup_records` 表保留 | 正式升级备份继续由系统升级 BFF 管理；旧结构后期仅做依赖评估 |

| 旧 Web 环境配置 | 无页面 | `/api/config/*` 前置返回 410 | 使用专用配置接口替代，旧实现暂时保留 |

## 3. 安全原则

隐藏菜单不等于删除能力。当前采用“正式模块、菜单和前端路由隐藏 + 服务端最前置统一 410 + 自动化不可达测试”的组合边界；这已经是当前私有化和公网部署共同采用的正式安全状态。后方同名 handler 即使仍保留在源码中，也不能绕过前置屏障被网络调用。

源码物理存在本身不列为当前安全缺口。直接删除可能与 Wizard、Office、工坊、数据库结构、共享工具或 npm 依赖产生冲突，因此不把“删除遗留源码”作为当前交付或验收的阻塞项。

## 4. 遗留代码依赖评估与分阶段整理（非当前安全待办）

当前不安排物理删除。后续只有在 ISO 冻结、依赖漏洞治理、维护成本明显上升，或某组代码已经确认完全无引用时，才按下列方式评估：

1. 逐组确认正式页面、Wizard、Office、工坊、报告、系统监控和启动流程没有复用。
2. 先核查模块导入、启动副作用、WebSocket、子进程、文件写入、数据库结构和 npm 依赖，再决定是否删除。
3. 每次只整理一个边界清楚的遗留模块，保留前置 410 和不可达测试，避免同一路径被以后意外重新开放。
4. 数据库表、持久化文件和生产数据不随源码整理自动删除；如确需处理，另行设计迁移、备份和回滚。
5. 每组整理后执行完整构建、四角色接口回归和生产启动验证，不进行一次性批量清理。

## 5. 验收标准

- 用户无法通过菜单或已知旧前端路由进入遗留页面。
- 九组明确停用的遗留前缀对任意方法和子路径稳定返回 `410 ENDPOINT_RETIRED`。
- 终端、桌面、旧备份、旧升级、Hermes、通用文件和旧配置不能作为正式公网 API 使用。
- 自动化测试证明后方遗留 handler 不可达；保留源码不影响当前安全验收。
- 后期若分组整理源码，入口、对话、Wizard/Office、工坊、报告、系统配置和升级功能不得回归。
