# 仪表盘时间范围统一与长区间查询修复规划

| 属性 | 内容 |
|---|---|
| 创建日期 | 2026-07-27 |
| 状态 | 第一阶段已实现并完成 237 发布验收 |
| 涉及模块 | 管理控制台仪表盘、通用时间范围组件 |
| 实施原则 | 替换仪表盘时间控件，保留统计链路，修复长区间展示和请求竞争 |
| 不涉及 | OpenClaw 源码、报告来源链路、会话管理、数据库迁移 |

## 1. 背景与已确认现象

仪表盘的“今天”和“7d”通常可用，但“30d”和较长自定义范围容易出现等待时间长、看起来没有刷新、日期与数据不一致或趋势没有覆盖完整时间范围的问题。

2026-07-27 只读排查确认：

- 237 当前约有 557 个会话记录文件，总量约 406MB；
- 相同 `sessions.usage` RPC 直接实测：
  - 7 天：57 个会话，约 135KB，约 1.8 秒；
  - 30 天：296 个会话，约 688KB，约 6.8 秒；
  - 90 天：306 个会话，约 723KB，约 6.9 秒；
- Gateway 在并发请求期间，部分 Usage 请求耗时达到 22～24 秒，但最终成功；
- Gateway 不存在“超过 7 天就不支持”的硬限制。

因此问题不在数据缺失或 Gateway 范围限制，主要来自仪表盘前端的展示截断、请求调度和时间交互。

## 2. 当前问题

### 2.1 趋势被固定截成最后 14 天

`Dashboard.vue` 使用 `dailyUsage.slice(-14)`。30 天及更长范围即使返回完整日数据，趋势仍只展示最后 14 个点，无法代表用户选择的完整范围。

### 2.2 查询中的新选择会被丢弃

`refreshDashboard()` 在 `refreshing=true` 时直接返回。用户在旧查询未结束时选择新范围，页面日期先变化，但新查询可能没有发出；旧结果返回后可能显示在新日期标签下。

### 2.3 旧结果可能覆盖新范围

当前没有请求代次或“最后一次请求生效”约束。WebSocket RPC 不能直接用浏览器 `AbortController` 取消，因此必须在页面状态层阻止过期响应写入。

### 2.4 后续查询缺少明确加载状态

第一次成功后 `hasUsageData=true`，后续长查询继续保留旧图表，整体加载遮罩不再出现。用户只能从刷新按钮的细小状态判断，容易认为点击未生效。

### 2.5 自定义时间交互不完整

当前使用两个原生 `date` 输入框：

- 只能选择日期，不能选择具体时间；
- 修改后只切换为 `custom`，不会确认并自动查询；
- 没有开始时间、结束时间和未来时间的完整校验；
- 没有取消、重置和当前生效范围的统一表达；
- 使用浏览器本地日期，没有与 BFF 服务器时间校准。

### 2.6 长区间返回浏览器的数据偏大

仪表盘调用 `sessions.usage(limit=1000)`，会把会话明细和聚合结果一起传回浏览器。30 天响应已经接近 700KB，仪表盘实际主要使用聚合结果和覆盖率，并不需要完整明细中的所有字段。

## 3. 方案决策

采用：

> 替换仪表盘原时间选择器，保留现有统计 RPC 和统计卡片，先修复前端请求与展示；完成实测后再决定是否增加 BFF 聚合缓存。

不采用：

- 继续在两个原生日期框上零散打补丁；
- 为时间选择修改 OpenClaw；
- 第一阶段同时重写仪表盘、报告管理器和告警页面；
- 未经实测直接新增复杂统计数据库。

该方案工作量中等，风险集中在仪表盘前端，可与报告、会话和 OpenClaw 链路隔离。

## 4. 目标交互

仪表盘使用与报告管理器一致的时间选择模式：

- 一个时间范围触发按钮；
- 预设：今天、最近 7 日、最近 30 日、本月、自定义；
- 自定义使用日期时间范围面板；
- 自定义范围有“确认”和“取消”；
- 触发按钮始终显示当前已经生效的开始和结束时间；
- 使用 BFF 响应的服务器时间作为“现在”的基准；
- 确认新范围后自动查询，不需要再点一次刷新；
- 刷新按钮仅表示重新查询当前已生效范围。

第一阶段不强制报告管理器和告警页面立即改用新组件，避免一次改动三个正式页面。

## 5. 实施阶段

### 阶段一：抽取通用时间范围模型

新增可复用的时间范围组件和纯函数工具，建议职责：

- `TimeRangePicker.vue`：弹层、预设、自定义面板、确认、取消；
- `time-range.ts`：预设计算、格式化、校验、区间天数和粒度计算；
- 组件输入：服务器当前时间、当前已生效范围、允许的预设；
- 组件输出：一次确认后的完整范围，不在选择过程中修改业务查询状态。

通用组件以报告管理器现有交互为依据，但不直接移动或破坏报告管理器代码。

### 阶段二：仪表盘替换时间控件

在 `Dashboard.vue`：

- 删除 `today/7d/30d` 按钮和两个原生日期框；
- 接入通用时间范围组件；
- 保持现有 Token/费用切换、统计卡片、趋势、结构和排行；
- 把显示范围和正在编辑范围分开；
- 使用统一的毫秒时间范围，在调用 Gateway 前再转换成 `YYYY-MM-DD`。

### 阶段三：修复请求调度

Usage 查询单独建立请求代次：

1. 每次确认范围递增 `usageRequestId`；
2. 请求携带自己的 ID 和范围快照；
3. 只有 ID 等于最新 ID 时才能更新页面；
4. 旧请求允许在后台完成，但结果被丢弃；
5. 用户在查询中再次选择范围时，新请求必须进入执行，不能因为 `refreshing` 被直接丢弃；
6. 页面摘要刷新与 Usage 刷新分离，避免任务、模型等概览请求阻塞时间范围切换。

加载表现：

- 保留旧数据，避免整个页面闪空；
- Usage 区域显示明确遮罩和“正在统计 YYYY-MM-DD 至 YYYY-MM-DD”；
- 查询完成后再切换范围标签和数据；
- 失败时保留上一份成功结果，同时显示失败范围和可重试入口。

### 阶段四：修复趋势粒度

删除固定 `slice(-14)`，按范围自动处理：

| 范围 | 图表粒度 |
|---|---|
| 1～31 天 | 按日，展示全部日期 |
| 32～180 天 | 按自然周汇总 |
| 181 天以上 | 按自然月汇总 |

汇总必须同时累加 Token、费用、消息、工具调用和错误数；坐标轴明确显示当前粒度。没有数据的日期是否补零，应与 Gateway 返回口径核对后确定，不能自行伪造活动数据。

### 阶段五：性能复测与可选 BFF 收口

前端修复发布前后分别测量 7、30、90 天：

- RPC 服务端耗时；
- 浏览器收到的字节数；
- 页面从确认到完成的耗时；
- 并发切换后的最终范围是否正确。

如果 30 天在生产负载下仍经常超过目标时间，再在 Admin BFF 增加仪表盘专用聚合接口：

- BFF 调用现有 Gateway RPC，不修改 OpenClaw；
- 只返回仪表盘需要的聚合字段；
- 相同用户范围和时间范围做短时缓存与 single-flight；
- 浏览器不再接收完整会话明细；
- 缓存必须包含数据范围、生成时间和失效规则。

这一步是测量后的第二阶段优化，不作为第一版替换控件的前置条件。

## 7. 验收标准

### 功能

- 今天、7 天、30 天、本月和自定义均可正常查询；
- 30 天趋势覆盖完整 30 天，不再只显示最后 14 天；
- 90 天范围按周展示，首尾日期与选择范围一致；
- 自定义范围确认后自动查询，取消不改变当前结果；
- 开始时间晚于结束时间、空范围和未来结束时间有明确提示；
- 刷新只重新查询当前生效范围。

### 并发与状态

- 连续选择 7 天、30 天、90 天，最终只能显示最后确认的 90 天结果；
- 旧请求结束时不能覆盖新结果；
- 查询中显示明确的目标范围；
- 查询失败保留上一份成功数据，并标明失败范围；
- Gateway 重连后只重试当前范围一次，不产生请求风暴。

### 性能目标

- 7 天正常负载目标小于 5 秒；
- 30 天正常负载目标小于 15 秒；
- 90 天允许更长，但必须持续显示加载状态且不能超时后静默；
- 浏览器主线程不因响应解析或图表点位过多而明显卡顿。

性能目标用于验收和决定是否实施 BFF 聚合缓存，不承诺改变 Gateway 本身的扫描耗时。

### 回归

- Token/费用切换、KPI、结构和排行口径不变；
- 仪表盘概览卡片、Gateway 状态和快捷入口不受影响；
- 报告管理器、告警页面、会话管理和升级模块测试通过；
- TypeScript、Vite 构建、Node 测试和 Vitest 全部通过。

### 10.3 BFF 聚合决策

本轮不新增仪表盘专用 BFF 聚合接口。理由：

- 237 只读基线中 30 日和 90 日 RPC 均约 6.8～6.9 秒，处于 30 日小于 15 秒的目标内；
- 当前最确定的问题是前端固定截断、请求竞争和加载反馈，第一阶段已经直接修复；
- 立即增加缓存会引入失效、用户隔离和统计口径的新复杂度，尚无必要。

237 发布后仍需记录 7、30、90 日真实耗时和响应体积。如果 30 日在正常负载下经常超过 15 秒，或并发时持续达到 22～24 秒，再启动第五阶段的 BFF 聚合与 single-flight 设计。
