# 单用户模块权限管理接口

| 属性 | 内容 |
|---|---|
| 日期 | 2026-08-31 |
| 状态 | 第二阶段正式接口基线 |
| 代码目标 | `server/lib/module-permissions.js`、`server/routes/module-permissions.js` |

## 1. 通用约束

所有接口使用 Bearer 登录认证。目录 key 和 effect 只接受服务端固定枚举；浏览器不能提交模块名称、REST 路径、RPC 方法、risk、locked、角色默认或最终值。第一版只有初始管理员可以读取单用户完整覆盖并执行 PUT/DELETE；普通管理员、审计、标准和基础用户均不能写。

当前登录用户的 `effectiveModules` 和 `permissionVersion` 通过登录及 `/api/auth/check` 返回，不需要调用目标用户管理接口。

有效模块在接口层的补充不变量：`audit` 直接控制审计列表与受控导出，不再叠加旧角色查看门禁；Gateway `status/health` 与 `system-presence/node.list` 一样登记到 `system`，因此个人 allow、角色默认和 deny 使用同一 resolver 结果。`GET /api/users` 对所有获准角色统一移除 `mustChangePassword`，但登录与 `/api/auth/check` 继续只向当前用户返回自己的首次改密状态。

## 2. GET `/api/module-permissions/catalog`

权限：登录。返回固定目录，不返回任何用户覆盖：

```json
{
  "ok": true,
  "modules": [
    {
      "moduleKey": "alerts.export",
      "name": "告警导出",
      "group": "业务管理",
      "risk": "medium",
      "dependencies": ["alerts.records"],
      "routes": ["/alerts"],
      "rest": ["POST /api/alerts/export"],
      "sse": [],
      "rpc": [],
      "dataScope": "当前页六个展示字段，最多100条"
    }
  ]
}
```

目录顺序稳定，由服务端定义；客户端不得追加自由文本 key。

## 3. GET `/api/users/:id/module-permissions`

权限：初始管理员。目标不存在返回 `404 USER_NOT_FOUND`。

```json
{
  "ok": true,
  "user": {
    "id": "target-id",
    "username": "operator01",
    "role": "standard",
    "isInitialAdmin": false
  },
  "permissionVersion": 3,
  "modules": [
    {
      "moduleKey": "cron",
      "defaultAllowed": false,
      "override": "allow",
      "effectiveAllowed": true,
      "locked": false,
      "lockReason": null,
      "risk": "high",
      "dependencies": []
    }
  ]
}
```

## 4. PUT `/api/users/:id/module-permissions`

权限：初始管理员。请求原子替换目标用户的全部覆盖：

```json
{
  "expectedVersion": 3,
  "overrides": [
    { "moduleKey": "cron", "effect": "allow" },
    { "moduleKey": "models", "effect": "deny" }
  ]
}
```

约束：

- `expectedVersion` 必须是非负安全整数。
- `overrides` 必须是数组；每个 key 最多一次。
- effect 只允许 `allow/deny`；`inherit` 通过省略该 key 表达。
- 拒绝未知 key、额外字段、锁定项和最终依赖冲突。
- 同角色默认相同方向的覆盖允许保存，仍明确表达个人强制值；删除后恢复跟随角色。
- 事务内比较版本、替换全部覆盖、版本加一并写审计。

成功返回与 GET 相同的最新完整投影。版本不匹配稳定返回：

```json
{
  "ok": false,
  "code": "PERMISSION_VERSION_CONFLICT",
  "error": "模块权限已被其他操作更新，请刷新后重试",
  "currentVersion": 4
}
```

HTTP 为 409，不覆盖当前数据。

## 5. DELETE `/api/users/:id/module-permissions`

权限：初始管理员。请求体：

```json
{ "expectedVersion": 4 }
```

事务内删除全部覆盖并将版本加一；空表删除也会形成一个新版本，保证并发客户端可观察本次恢复默认操作。成功返回最新完整投影。

若恢复角色默认会触发依赖冲突，说明数据库或目录不一致，返回 `409 MODULE_PERMISSION_DEPENDENCY_CONFLICT`，不修改数据。

## 6. 认证投影

`POST /api/auth/login` 与 `GET /api/auth/check` 的 user 增加：

```json
{
  "effectiveModules": {
    "dashboard": true,
    "alerts.records": true,
    "alerts.notifications": true,
    "alerts.export": true
  },
  "permissionVersion": 3
}
```

只返回布尔最终值和版本，不返回其他用户、操作者或审计差异。

## 7. 稳定错误码

| HTTP | code | 条件 |
|---:|---|---|
| 400 | `INVALID_PERMISSION_PAYLOAD` | 请求结构、expectedVersion 或额外字段无效 |
| 400 | `UNKNOWN_MODULE_PERMISSION_KEY` | key 不在固定目录 |
| 400 | `INVALID_MODULE_PERMISSION_EFFECT` | effect 不是 allow/deny |
| 400 | `DUPLICATE_MODULE_PERMISSION_KEY` | 同一请求重复 key |
| 400 | `MODULE_PERMISSION_LOCKED` | 尝试覆盖目标用户锁定模块 |
| 409 | `MODULE_PERMISSION_DEPENDENCY_CONFLICT` | 最终允许项缺少依赖 |
| 409 | `PERMISSION_VERSION_CONFLICT` | expectedVersion 与当前版本不同 |
| 403 | `INITIAL_ADMIN_REQUIRED` | 非初始管理员读取目标覆盖或写入 |
| 404 | `USER_NOT_FOUND` | 目标用户不存在 |

## 8. 审计

一次 PUT/DELETE 在同一事务中写一条版本/增加/削减/恢复计数摘要，并按有界长度写一条或多条逐 key 前后差异。差异以 `i/a/d` 表示 inherit/allow/deny，以 `0/1` 表示最终拒绝/允许；每个变更 key 只出现一次，避免受审计字段 500 字符上限截断。审计记录操作者 ID/用户名/角色、目标用户 ID/用户名和旧/新版本，不记录密码、Token、Cookie、请求头、敏感配置或完整请求体。

权限写入成功后仅向目标用户发送 `permissionsChanged`。事件不含覆盖明细；浏览器必须重新获取认证投影。
