## 1. 背景

2026-07-17 在 237 的共享插件目录中安装钉钉插件后，企业微信插件的 `openclaw` peer 依赖解析失效；Gateway 重启后企业微信加载失败。2026-07-20 已按企业微信官方安装器完成修复，并为企业微信插件建立独立 peer 依赖链接。

该事件证明：频道插件不能在客户运行环境中逐个原地安装或升级后直接结束。一次插件变更必须被视为对全部频道运行时的变更，并统一验证、失败回滚。

## 3. 是否给每个频道手工建立依赖链接

不采用“给所有频道统一执行 `ln -s`”的做法，原因如下：

1. 各插件的 peer 依赖名称、版本范围、入口和官方安装方式不同；没有声明依赖的插件不应被强行注入。
2. 软链接只解决模块可见性，不能证明核心版本满足插件兼容范围，也不能解决 API 变更。
3. 手工链接不进入升级清单、校验和与回滚记录，客户升级后容易再次丢失。
4. 当前飞书候选冻结版本已明确，但本次实操证明单插件安装会重建共享 npm 树；升级后若只检查目标插件，会遗漏其他频道的依赖破坏。

正确做法是：ISO/升级构建程序读取每个插件的 `peerDependencies`，使用插件官方安装器或受控依赖解析步骤生成插件自己的运行依赖；结果写入发布清单并做运行时验证。当前企业微信、钉钉和飞书都具有各自的独立 `openclaw` peer 链接，但这是依赖声明和兼容校验后的结果，不是对所有未来插件机械复制的命令模板。

未来若增加 QQ、个人微信或其他频道，应先检查该插件是否声明 `openclaw` peer 依赖：声明时由构建/升级程序创建并验证插件自己的依赖解析；未声明或采用其他运行方式时不强加链接。无论是否需要链接，新增频道都必须纳入全插件重启检查和失败自动回滚。

## 4. ISO 首次交付要求

ISO 构建阶段一次性完成以下工作，客户页面不执行插件安装：

1. 固定 Gateway 核心、飞书、钉钉、企业微信插件的精确版本，不使用运行时 `latest`。
2. 记录每个包的来源、版本、校验和、peer 依赖范围、安装目录和运行时入口。
3. 按固定顺序在干净构建目录安装全部组件，禁止在黄金镜像运行目录中临时补装。
4. 对所有插件执行 runtime inspect，对所有已配置频道执行 status 检查。
5. 完成一次 Gateway 冷启动/重启恢复测试，再冻结 ISO。
6. 删除测试频道凭据和测试数据后生成最终镜像校验和与冻结记录。

## 5. 客户升级事务

客户升级不能让管理员逐项排查，升级服务必须自动执行：

```text
校验升级包与兼容矩阵
→ 备份配置、当前程序和完整插件依赖目录
→ 在版本化临时目录安装新核心与全部受影响插件
→ 静态检查包版本、peer 依赖和入口
→ 切换候选版本并重启 Gateway
→ 检查 Gateway、全部插件和全部已启用频道
→ 全部通过后提交；任一失败则自动恢复旧目录与配置并再次启动
```

升级包 manifest 至少包含：

- Gateway 核心版本与校验和；
- 所有频道插件的精确版本、校验和及兼容核心范围；
- 受影响组件和重启要求；
- 安装前检查、安装后检查和最长等待时间；
- 回滚所需目录、配置版本和回滚后检查；
- 禁止客户包覆盖的持久化数据及密钥范围。

## 6. 自动检查与失败条件

升级服务应使用绝对程序路径执行检查，不依赖交互式 shell 的 `PATH`。至少包括：

```bash
openclaw gateway status --deep --require-rpc
openclaw plugins inspect wecom-openclaw-plugin --runtime
openclaw plugins inspect dingtalk-connector --runtime
openclaw plugins inspect openclaw-lark --runtime
openclaw channels status --probe
openclaw plugins registry --refresh --json
```

实际插件 ID 由冻结清单提供，不能在客户现场猜测。出现以下任一情况必须自动回滚：

- Gateway RPC 不可用或服务未进入稳定运行态；
- 任一交付插件不是 `loaded`；
- 任一升级前已启用频道未恢复 `running`；
- 出现 `ERR_MODULE_NOT_FOUND`、入口缺失、peer 版本不兼容、重复插件 ID、陈旧插件索引或配置无法解析；
- 检查超时、恢复后版本与清单不一致，或配置/持久化目录校验失败。

## 7. 当前实现缺口与后续顺序

当前系统升级模块已有包校验、任务进度、Skill 回滚和备份删除，但核心、前端及频道插件的专用健康检查与自动回滚尚未完成，因此不得开放客户自行升级这些组件。

后续顺序：

1. 在克隆环境验证 Gateway `2026.5.4` 与飞书 `openclaw-lark@2026.5.20` 候选组合的冷启动、断网重连和失败回滚；
2. 定义机器可读的核心/频道兼容矩阵和发布清单字段；
3. 在升级服务实现版本化暂存、全插件检查、失败自动回滚和任务审计；
4. 在克隆/准生产环境演练成功与失败升级，不直接以客户环境作为首次验证场所；
5. 验收完成后才允许系统升级页面接收包含核心或频道插件的升级包。

## 8. 验收结论

“配置已保存”只代表频道配置存在；“插件已加载、频道运行、真实收发、重启恢复、升级失败可自动回滚”全部通过后，才能声明频道及其升级能力可交付。
