## 1. 结论与边界

本批只提供 ISO/部署配置，不修改后端应用代码，不执行全盘日志扫描或清理。三个模板分别由 Caddy、logrotate 和 journald 原生机制管理：

| 类别 | 精确目标 | 轮转与压缩 | 最长期限 |
|---|---|---|---:|
| Caddy 访问日志 | `/var/log/gaiop/caddy/access.log` | 每日 00:00 或 100 MiB；Caddy 原生 gzip | 365 天 |
| NAPM 原始 Syslog | `/var/log/netinside/syslog.log` | 每日重命名轮转；上一段延迟一轮后 gzip | 365 天 |
| journald 与其中的认证/安全事件 | `/var/log/journal` 的 journald 原生存储 | 单个 journal 最长 1 天；journald 原生压缩 | 180 天 |

不在本批范围内：`alerts.jsonl`、解析告警、Admin/Upgrade/清理核心审计、报告、会话、数据库、应用文件日志、Caddy 运行日志、rsyslog 自身其他输出、原始操作系统文本安全日志、容量水位和全盘清理。模板没有通配日志路径，也没有删除脚本。

## 2. 配置说明

### 2.1 Caddy 访问日志

`deploy/iso/caddy/gaiop-access-log.caddy` 是只能在 GAIOP HTTPS site block 内导入一次的片段。它使用 `/var/log/gaiop/caddy/access.log`，显式设置：

- `roll_at 00:00` 和 `roll_size 100MiB`；不设置 `roll_local_time`，轮转文件名保持 Caddy 默认 UTC 时间戳；
- `roll_keep 0` 关闭默认“仅保留固定份数”，避免在 365 天之前因高流量产生较多分段而提前删除；
- `roll_keep_for 8760h` 保留轮转段 365 天；不设置 `roll_uncompressed`，历史段使用 Caddy 默认 gzip；
- 删除认证、代理认证、Cookie、API Key、认证 Token、响应 Cookie 及任何请求/响应正文日志字段；
- 将 URI 的整个查询串替换为固定标记，而不是依赖有限的敏感参数名单。路径仍可用于入口诊断，查询值不会进入访问日志。

Caddy 对同一输出文件的轮转参数变更需要重启进程才能可靠生效；部署时不能只 reload。实际 Caddyfile 可能含认证配置，预检、备份和故障输出均不得打印其正文。

### 2.2 原始 Syslog

`deploy/iso/logrotate/gaiop-netinside-syslog` 只登记精确路径 `/var/log/netinside/syslog.log`：

- `daily`、`maxage 365`、`rotate -1`：只按期限淘汰已轮转段，不受全局默认份数限制；期限仅在每日轮转时检查，因此刚超过边界的段可能到下一次轮转才删除，不会早删；
- `create 0640` 继承当前文件属主和属组，不在模板中猜测生产账户；
- `compress + delaycompress`：历史段 gzip，刚轮转段保留一轮不压缩，给按文件名跟随的接收器追完旧文件；
- `noallowhardlink` 且不使用 `copytruncate`，避免硬链接扩大影响和复制/截断竞态；
- 轮转后向 `rsyslog.service` 主进程发送 HUP，使写入端重新打开新文件。命令失败会使 logrotate 报错，不静默掩盖。

GAIOP 接收器的已知部署契约是按文件名执行 `tail -F`，不是固定跟随旧 inode。生产启用前仍必须核查 237 现用代码和实际服务定义；若现场不符合此契约，停止安装，不得用重启接收器或 `copytruncate` 临时绕过。

### 2.3 journald 与认证/安全日志

`deploy/iso/journald/60-gaiop-retention.conf` 设置 `Storage=persistent`、`Compress=yes`、`MaxFileSec=1day` 和 `MaxRetentionSec=180day`。它让 journald 中的系统及认证/安全事件使用持久化存储并执行 180 天期限。

模板没有设置 `SystemMaxUse`、`RuntimeMaxUse`、`SystemKeepFree`、`RuntimeKeepFree`、`SystemMaxFiles`、`RuntimeMaxFiles` 或文件大小容量上限。本批不以容量或文件数量提前淘汰。journald 在磁盘耗尽等系统保护条件下的行为属于后续容量治理，ISO 必须据实际日志速率预留能覆盖 180 天的空间。

若目标系统还把认证/安全事件另写为 `/var/log/auth.log`、`/var/log/secure` 或其他文本文件，本模板不管理这些未知文件；部署负责人应先确认权威存储是否为 journald，再决定单独后续策略，不能把它们加入本配置的通配符。

## 3. 发布前只读现场核查

2026-08-09 从当前工作环境对 237 执行批处理 SSH 只读探测时认证失败，未读取 Caddyfile、日志正文、凭据或生产环境文件。因此以下项目必须在获得操作系统变更批准、安装模板之前由 237 现场重新核查，历史发布记录不能替代：

1. `readlink -f /etc/caddy/Caddyfile`、Caddy 版本、service unit 路径、实际 `User/Group`、GAIOP site block 的唯一导入点，以及是否已有访问日志配置；只输出路径/版本/元数据，不打印 Caddyfile。
2. `/var/log/gaiop/caddy` 解析后真实路径、目录链无符号链接、所在文件系统和 Caddy 账户写权限。
3. `readlink -f /var/log/netinside/syslog.log`、文件类型、目录链、属主/属组/权限；确认它仍是 rsyslog 的 GAIOP 原始输入文件，且没有另一份 logrotate 规则登记同一路径。
4. `rsyslog.service` 当前 active 状态、HUP 重开文件支持，以及 GAIOP Syslog 接收器的实际 unit、服务管理范围和当前代码仍使用 `tail -F`。
5. systemd 版本、`/var/log/journal` 解析路径与持久化状态、现有 journald drop-in 冲突，以及认证/安全事件确实进入 system journal。只核查字段和计数，不读取事件正文。
6. 估算三类日志 365/365/180 天的容量；若空间不足，先扩容或完成后续容量治理，不得擅自缩短期限或添加份数上限。

任一路径越界、为符号链接、归属不明、存在重复管理规则或服务契约不符，都应中止部署。

## 4. 安装流程（需单独批准后执行）

以下是 ISO/准生产安装说明，不是本次对 237 已执行的命令。

1. 先以只读方式运行静态检查：

   ```bash
   node deploy/iso/scripts/validate-system-entry-log-retention.mjs
   bash deploy/iso/scripts/validate-system-entry-log-retention-linux.sh --templates
   ```

2. 备份当前 Caddy 配置、journald drop-in 清单和 logrotate 登记状态到受限部署备份目录。备份可能含认证配置，不得打印、提交或放宽权限。记录文件计数和字节数，不读取日志正文。
3. 按实时核查的 Caddy 账户创建 `/var/log/gaiop/caddy`，确认目录链无符号链接；将 Caddy 片段安装为 `/etc/caddy/gaiop-access-log.caddy`，在唯一 GAIOP HTTPS site block 中导入。先 `caddy validate`，再受控 `systemctl restart caddy`，验证 80/443、SSE、健康接口和内部端口边界。
4. 将 Syslog 模板安装为 `/etc/logrotate.d/gaiop-netinside-syslog`，权限 `root:root 0644`。先执行 `logrotate --debug`。正常启用依赖系统已有的 `logrotate.timer` 或等价每日调度，不增加另一套删除 timer。
5. 将 journald 模板安装为 `/etc/systemd/journald.conf.d/60-gaiop-retention.conf`，先用 `systemd-analyze cat-config systemd/journald.conf` 核查合并结果，再受控重启 `systemd-journald` 并执行 `journalctl --flush`。验证 system/user services 和认证事件采集，不输出事件正文。
6. 安装后运行只读检查：

   ```bash
   bash deploy/iso/scripts/validate-system-entry-log-retention-linux.sh --installed
   ```

7. 仅在明确批准“制造一次轮转和无敏感测试消息”后，才执行连续性验证：

   ```bash
   sudo GAIOP_LOG_RETENTION_LIVE_ROTATION_APPROVED=YES \
     bash deploy/iso/scripts/validate-system-entry-log-retention-linux.sh --exercise-syslog-rotation
   ```

   该模式强制轮转登记的 Syslog 文件、检查 inode 已变化、确认 rsyslog active，并写入固定无敏感测试标记后仅通过字节数增长验证继续写入；它不读取日志正文。若接收器为用户级 unit，必须同时传入现场确认的 `GAIOP_SYSLOG_RECEIVER_USER`，脚本才会以该账户验证 unit 仍为 active；随后还需只看健康元数据确认处理时间继续前进且新告警链路正常。

## 5. 验证要求

- Caddy：`caddy validate` 成功；当前 `access.log` 仍存在且为普通文件；轮转段命名和 `.gz` 符合原生规则；构造带认证头、Cookie、请求正文和敏感查询值的准生产请求后，仅通过结构化字段检查确认值不存在，验证样本本身不得含真实凭据。
- Syslog：`logrotate --debug` 成功；当前文件不被当作过期段删除；轮转后 inode 变化、rsyslog 继续向新文件写入、接收器保持 active 并继续推进健康状态；第一段因 `delaycompress` 暂不压缩，下一轮后成为 `.gz`。
- journald：合并配置只有 180 天期限、单日分段和压缩，没有新增大小/数量上限；重启后 persistent 生效，system/user unit 与认证/安全事件仍可按元数据查询。
- 到期边界：恰好等于期限仍保护，严格早于 UTC 截止线才视为到期；原生工具可能在下一次轮转时才实际淘汰，因此允许晚删，不允许早删。
- 范围：发布前后分别记录三个当前文件/存储的数量和字节数；安装配置本身不应删除任何现有日志。`alerts.jsonl`、审计、报告、会话和数据库计数不得变化。

## 6. 关闭与回滚

关闭或回滚均只撤销配置，不删除已经产生的日志：

1. 从活动 GAIOP site block 移除唯一导入，先 `caddy validate`，再重启 Caddy；保留 `/var/log/gaiop/caddy` 供后续受控处置。
2. 将 `/etc/logrotate.d/gaiop-netinside-syslog` 移出 logrotate 扫描目录并重新执行 `logrotate --debug`；不删除 `syslog.log` 或任何轮转段，rsyslog 和接收器继续运行。
3. 移除或恢复 journald drop-in 后，用 `systemd-analyze cat-config` 确认合并结果，再受控重启 journald；不得执行 `journalctl --vacuum-*`。
4. 复测 Caddy、rsyslog、接收器、journald、GAIOP 公网入口和内部服务，并比较回滚前后日志文件数量。失败时恢复受限备份，但不得输出备份中的认证信息。

本批没有修改 237 的 Caddy 配置、rsyslog、journald 或任何生产日志，也没有执行真实轮转、压缩或删除。
