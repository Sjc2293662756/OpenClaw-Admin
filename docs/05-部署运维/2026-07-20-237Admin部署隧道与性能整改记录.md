## 1. Gateway 会话恢复与首次正式部署

### 1.1 现象与根因

用户登录后曾持续重连，Usage 接口提示 GAIOP 智能体服务未连接。BFF 健康接口可用但 Gateway 为 `disconnected`。脱敏检查确认 BFF 服务账户到本机 `18789` TCP 可达，因此排除基础本机网络不通。

按 OpenClaw `v2026.5.4` Gateway 协议，带共享认证的本机受信任后端可使用 `client.id=gateway-client`、`client.mode=backend` 建连而不携带设备身份。Admin BFF 对仅限 `127.0.0.1`、`::1` 或 `localhost` 且已配置共享认证的连接采用此兼容身份；非本机连接仍保留既有 CLI/设备签名流程。协议版本固定为 3，未升级 Gateway。

### 1.2 发布与回滚

最终成功批次为 `20260720T095930Z`。发布器切换前保留版本化备份，未覆盖 `.env`、SQLite、报告数据或密钥。启动验证只接受 `127.0.0.1:3000` 或 `[::1]:3000`，同时要求健康接口显示 Gateway `connected`。最终服务为 active、未 enable，经本机 `127.0.0.1:3005 -> 237:127.0.0.1:3000` 隧道健康检查成功。

## 2. 静态资源与 SSH 传输性能

### 2.1 HTTP 压缩和缓存

用户反馈隧道访问慢、页面持续加载。定位结果表明服务器内 BFF 健康接口约 1–2 ms、Gateway 已连接、负载正常；主要缺口是 BFF 原先未对普通 API/静态资源启用内容压缩，且前端存在较大 JavaScript 资源。

修复内容：

- 增加 `compression` 生产依赖；
- 对普通 API 和静态资源启用压缩，明确排除 SSE `/api/events`；
- 带指纹资源使用一年 `immutable` 缓存，入口 HTML 使用 `no-cache`。

最终成功批次为 `20260720T140105Z`。经 3005 隧道验证 HTTP 200、Gateway `connected`，入口资源返回压缩与 immutable 缓存头。准备阶段曾超过本机监督窗口，旧版已从版本化备份恢复；失败目录保留，未删除。

### 2.2 性能结论

压缩后，服务器内 BFF 健康接口仍约 1–2 ms，但旧 Node/ssh2 隧道的复用 HTTP 连接出现并发分批和长尾；12 个并发健康请求总耗时约 1.06 秒。瓶颈位于 SSH 转发的 channel 调度与公网往返，不是 BFF 计算或 Gateway 基础连接。

本地 ssh2 工具已启用 `TCP_NODELAY`，但这只是局部优化。正式产品入口仍应保持 BFF 为唯一 Web 决策入口：私网版使用内网/VPN 的 HTTPS 反向代理直达 BFF；公网版由 Caddy/443 提供 TLS、访问控制和反向代理。禁止直接暴露 BFF `3000` 或 Gateway `18789`。

## 3. 切换为原生 OpenSSH 隧道

为改善 ssh2 并发调度，已将本机 3005 默认隧道切换为原生 OpenSSH。修改 `authorized_keys` 前创建备份 `/home/netinside/.ssh/authorized_keys.gaiop-backup-20260720T143225Z`，仅追加专用公钥并校正权限；私钥没有被输出、上传或提交。

同一组 12 并发健康请求中，旧 Node/ssh2 隧道约 1,597 ms，原生 OpenSSH 约 306 ms；首页及三个入口资源从约 11,411 ms 降至约 880 ms。仍存在公网到 SSH 的持续传输长尾，因此这不是正式公网入口的替代方案。

本机回滚仅切换隧道实现：关闭当前 3005 `ssh.exe` 后执行 `Start-AdminBff237Tunnel.ps1 -UseLegacyNodeTunnel`。若需要撤销服务器专用公钥，必须另行授权并精确恢复相应 `authorized_keys` 备份或删除带指定注释的单行公钥。

## 4. 仪表盘分区加载优化与发布

仪表盘曾因首屏并发调用会话、任务、模型、Skills、配置、`sessions.usage`、`usage.cost`，且由一个最外层加载遮罩等待全部完成，导致进入页面约两秒整页转圈。前端改为页面骨架立即显示，将基础统计与 Usage/KPI/趋势拆为独立加载区；`sessions.usage` 作为主数据源，`usage.cost` 仅在主数据不完整或失败时回退调用。

首次批次 `20260720T145336Z` 因启动验证器误判监听为 wildcard 而按安全策略回滚，未产生公网监听。验证器随后修正为使用 `ss -ltnH` 精确只接受 `127.0.0.1:3000` 或 `[::1]:3000`，对 `0.0.0.0:3000`、`[::]:3000`、`*:3000` 或混合监听仍拒绝。

最终成功批次 `20260720T145954Z`：备份、校验、依赖准备、发布切换和启动验证均完成，结果为 `admin-started-loopback-verified`、监听 `loopback-ipv4`。经 3005 健康接口 HTTP 200、Gateway `connected`；远端仪表盘分块与本地构建的字节数和 SHA-256 一致。

## 5. 共同安全边界

上述所有操作均未读取或记录环境变量值、密码、Token、私钥、频道 Secret 或客户配置；未修改 Caddy、443、防火墙、Gateway 配置、Syslog 接收器、频道插件或公网路由。

每个发布批次均使用对应 `/var/backups/gaiop/admin-prestage-<release-id>` 目录回滚。执行发布、停止、启动、回滚、日志读取或隧道重建前必须获得单次明确授权。
