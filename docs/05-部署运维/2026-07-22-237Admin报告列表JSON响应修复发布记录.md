因此将已登录列表处理中的未捕获异常作为防护缺口处理：Express 默认错误页是 HTML，旧前端无条件调用 `response.json()`，使真实错误被覆盖为 JSON 解析异常。

## 4. 发布期间发现的 ACL 回归与修复

本批次初次目录切换后，受控核对发现 Gateway 对 `/var/lib/gaiop/reports` 从 `read-write` 降为 `read-only`。原因是旧发布器对已存在的正式报告目录执行带模式的 `install -d`，重设了 ACL mask。

处理方式：

1. 已将发布前 ACL 备份到 `/var/backups/gaiop/admin-report-acl-20260722T035343Z`；
2. 仅恢复 `netinside` 对正式报告目录及新建子项的读、写、穿越权限；不修改报告文件；
3. 复核 Gateway 权限恢复为 `read-write`；
4. 本地受控发布脚本已改为：仅在正式报告目录不存在时创建，已有目录不再重设权限或 ACL mask。

用户在发布后实际访问列表时，BFF 返回 `REPORT_LIST_FAILED`。受控错误类别确认真实根因是：Gateway 以 `netinside` 创建的报告用户/类型子目录没有给 BFF 服务账户 `gaiop` 继承访问 ACL；根目录本身可访问，故首次目录级核对未暴露该问题。

已在独立递归 ACL 备份后完成精确修复：

- 现有报告目录的子目录同时允许 `gaiop` 与 `netinside` 读、写、穿越；
- 现有报告和审计 JSON 同时允许二者读取，且后续新建子项继承所需 ACL；
- 不读取、不输出、不修改报告内容；不重启 BFF 或 Gateway；
- Gateway 再次核对为 `read-write`，BFF 服务账户可读取整棵归档目录；
- 以 BFF 运行账户执行、但使用内存数据库的归档同步探针通过，覆盖与报告列表相同的文件扫描与审计解析逻辑。
