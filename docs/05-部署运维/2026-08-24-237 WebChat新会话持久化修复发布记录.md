# 2026-08-24 237 WebChat 新会话持久化修复发布记录

## 1. 问题

WebChat 首次发送长报告请求时，实时内容可以显示，但切换会话或刷新页面后，消息和左侧历史会话消失。普通短问答偶尔正常，导致问题看起来像报告渲染异常。

## 2. 根因

237 最终只读证据确认，这是新 WebChat 会话首条消息的持久化契约错误，不是报告内容、Markdown 渲染或留存机制问题：

- 异常会话 `agent:main:main:dm:webchat-1a37...` 已登记在 Admin `workspace_sessions`，实时报告也已生成，但整个会话键不在 Gateway `sessions.json` 中；
- 较早使用 `/new` 的异常会话虽进入 Gateway，但 transcript 只有初始化提示和 assistant 报告，没有 user 回合；
- 普通对话偶尔正常，是因为裸 `chat.send` 对一个尚未登记的任意新键可以启动运行，却不保证把该键原子登记到 Gateway 会话索引；长报告更稳定地暴露这个时间窗；
- 报告归因 Sidecar 按真实 Gateway 会话键读取 Web 来源签名。任务运行没有形成同一持久化会话时，报告文件仍可能归档，但来源渠道和用户无法可靠关联。

因此，先前的“`/new` 后等待”以及“去掉 `/new` 后直接 `chat.send`”都只能改变竞态窗口，不能满足“会话登记、transcript、首条用户消息、报告归属使用同一会话键”的原子要求。

## 3. 最终修复

- 复用 237 当前 OpenClaw `2026.5.4` 已有正式 RPC `sessions.create`，不修改 OpenClaw/Gateway 核心；
- BFF 在一个受控请求中登记用户归属、写入报告来源签名，再调用 `sessions.create({ key, message })`；Gateway 在同一服务端流程中写入 `sessions.json`、确保 transcript 并启动首条消息；
- 报告来源签名启用时，签名快照必须先成功落盘；随后只有 Gateway 返回相同会话键且明确 `runStarted=true`，BFF 才向前端返回成功。来源快照失败、断连、键不一致、首条消息未启动或运行错误均不会启动/暴露半成功会话；
- 前端接管 BFF 已启动的运行，只展示首条用户消息并刷新历史，不再重复调用 `chat.send`；已有会话的后续消息仍走原发送流程；
- 空会话创建与“创建并发送首条消息”继续保持两个明确入口，避免 `/new`、裸 `chat.send` 与正式创建语义再次混用；
- 来源签名与原子创建使用完全相同的 `sessionKey`，后续报告归档可以恢复 Web 渠道、当前用户、会话和数据源归属。

## 8. 二次问题核查与修正（2026-08-24）

首次发布后发现，新报告会话仍可能只保留机器人消息。只读 transcript 核对结果为：

- `webchat-5f9a...` 仅有 `✅ New session started.` 和“报告已生成”两条 assistant 消息；
- 同期普通会话包含完整的 `user -> assistant -> tool` 顺序；
- 因此确认是 `/new` RPC 已返回，但 Gateway transcript 尚未落盘时，首条报告请求立即进入，初始化时序吞掉了用户回合。

本次修正 `sessionStore.createSession()`：发送 `/new` 后，以同一 `sessionKey` 轮询 `chat.history`，确认至少有一条初始化历史后才返回给 ChatPage；最多等待约 7.6 秒，仍未确认则中止发送并保留用户输入。这样不再用实时 assistant 内容或本地缓存假造用户历史。

本节对应代码和测试在后续提交中补录，发布前必须重新执行构建、会话测试和 237 受控启动验证。
