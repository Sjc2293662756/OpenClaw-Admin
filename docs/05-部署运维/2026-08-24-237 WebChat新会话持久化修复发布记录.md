# 2026-08-24 237 WebChat 新会话持久化修复发布记录

## 1. 问题

WebChat 首次发送长报告请求时，实时内容可以显示，但切换会话或刷新页面后，消息和左侧历史会话消失。普通短问答偶尔正常，导致问题看起来像报告渲染异常。

## 2. 根因

最终代码审查确认，问题不是“缺少 `/new` 初始化”，而是 2026-08-24 的首次修复错误地把工作台从原有的“Admin BFF 签发唯一会话键后直接发送首条正式消息”改成了“先发送 `/new`，再发送首条正式消息”。

`/new` 是对已有会话上下文的重置命令，不是全新唯一 WebChat 会话的必需创建步骤。Gateway 对 `/new` 的 RPC 确认、transcript 重置落盘和随后长时间报告请求之间存在竞态；轮询到初始化提示只能证明提示可读，不能证明重置生命周期已经完全结束。因此报告回复可能写入，而紧邻重置的用户回合缺失。

这不是报告内容、Markdown 渲染、报告存储或留存机制问题。报告请求只是执行时间长，更容易暴露同一会话初始化竞态。

## 3. 最终修复

- ChatPage 恢复经过生产使用验证的顺序：BFF 登记并签发全新唯一会话键 -> 直接发送首条正式需求；
- 工作台首条发送不再调用 `/new`，报告与普通问答共用完全相同的发送路径；
- 将原 `createSession()` 更名为 `createInitializedSession()`，明确它只供会话管理、Office、MyWorld 的“创建空会话”入口使用，防止工作台再次误用；
- 保留空会话入口的 `/new` 初始化确认；这些入口不会在返回前自动紧接首条业务消息，不存在本次竞态；
- 不新增 Gateway 协议，不修改 OpenClaw 核心、频道插件或报告存储；
- 增加回归测试，锁定工作台会话签发过程不得发送 `/new` 或读取初始化历史。

## 8. 二次问题核查与修正（2026-08-24）

首次发布后发现，新报告会话仍可能只保留机器人消息。只读 transcript 核对结果为：

- `webchat-5f9a...` 仅有 `✅ New session started.` 和“报告已生成”两条 assistant 消息；
- 同期普通会话包含完整的 `user -> assistant -> tool` 顺序；
- 因此确认是 `/new` RPC 已返回，但 Gateway transcript 尚未落盘时，首条报告请求立即进入，初始化时序吞掉了用户回合。

本次修正 `sessionStore.createSession()`：发送 `/new` 后，以同一 `sessionKey` 轮询 `chat.history`，确认至少有一条初始化历史后才返回给 ChatPage；最多等待约 7.6 秒，仍未确认则中止发送并保留用户输入。这样不再用实时 assistant 内容或本地缓存假造用户历史。

本节对应代码和测试在后续提交中补录，发布前必须重新执行构建、会话测试和 237 受控启动验证。

## 10. 最终代码审查与第三次修正（2026-08-24）

二次修正上线后仍出现“只有机器人回复、用户消息未记录”，证明“看到 `/new` 初始化历史后再发送”并不能消除竞态。进一步回溯 Git 历史发现：

- `bcfcbc5`（2026-08-24）把 ChatPage 错误改为复用发送 `/new` 的旧 `createSession()`，是本次反复异常的直接回归点；
- `d34a77c` 仅增加等待，没有撤掉重置命令，因此不能从协议层解决问题。

最终修正撤销 ChatPage 对重置式创建流程的复用，并通过 API 更名隔离两类语义。会话管理、Office、MyWorld 只创建空会话，不会自动紧接业务消息；已有会话的显式“新会话/重置”操作也仍保留原语义。除这些明确入口外，前端没有其他 `/new` 发送路径。
