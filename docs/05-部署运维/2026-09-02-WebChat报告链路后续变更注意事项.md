# WebChat 报告链路后续变更注意事项

## 级别与目的

本项为**常规变更注意事项**，不是全仓库最高级门禁，也不阻断与报告链路无关的前端、BFF 或文档修改。其目的是提醒后续维护者：WebChat 页面出现“报告已生成”只证明回复文本存在，不能单独证明正式报告、附件卡片和下载链路已经成功。

下列任务需要阅读并执行本文的最小核对：

- 修改或发布报告 Skill、报告存储/生成服务、OpenClaw/Gateway 插件或 WebChat 报告来源契约；
- 使用后端快照、升级包或回滚包更新 237 运行时；
- 排查“报告生成成功但附件卡片不出现”、报告未登记或下载不可见；
- 修改 Admin 的报告登记、报告 API、卡片关联或 transcript 投影。

纯样式、无关页面、无关 BFF 路由和普通文档任务不需要因此扩大验证范围。

## 必须保留的链路契约

1. 正式报告目录保持 `GAIOP_REPORTS_DIR=/var/lib/gaiop/reports`。
2. 每份正式报告必须有配对审计 JSON，并进入 Admin `report_files` 登记。
3. WebChat 保持原生回合：`user -> toolCall -> toolResult -> assistant`。
4. 自动 `reply_dispatch` 只用于明确指定的外部频道，不截断或替代 WebChat 原生回合。
   渠道字段可能被错误继承，不能只用 `channelId` 放行；精确
   `agent:main:main:dm:webchat-*` `sessionKey` 必须优先作为自动派发的负向门禁。
5. 报告来源只使用可信的会话、用户、来源消息 ID 和来源预览；不得按文件名、时间、最近消息或会话末尾猜测。
6. 卡片继续复用既有 `/api/reports` 和 `/api/reports/:id/download` 权限边界，不新建第二套存储、下载或授权体系。

## 变更与发布时的最小核对

- 先比较当前生产运行时文件与待发布内容，禁止用旧快照覆盖整个 OpenClaw 工作区。
- 同时核对 workspace 插件副本、extension 真实加载副本和 extension loader；三者用途和哈希必须以当前生产事实为准。只修一个候选副本、只数 guard 字符串或只重启服务，均不能证明真实 WebChat turn 已避开自动派发。
- 发布后核对生产实际加载文件的 SHA-256 或等价运行时标识，不能只看 Git 提交。
- 至少确认：原生工具回合存在、正式报告和审计成对、`report_files` 已登记、来源关系完整。
- 若任务涉及卡片，再确认 `/api/reports` 按当前用户和精确会话返回，卡片在实时消息转持久历史后不消失、不重复、不跨会话。
- 没有生产证据证明上游缺字段时，优先限定在 Admin 前端/BFF 排查；确认上游契约退化后，再做对应的最小上游修复。
- 无法取得指定故障会话 key 时，不得使用“最新会话”或邻近会话代替；将会话级验收明确记录为未执行。

## 故障定位顺序

按以下顺序逐层核对，在哪一层首次失配，就把根因限定在哪一层：

`报告完成 -> 正式文件/审计 -> report_files -> /api/reports -> 完成信号重查 -> 来源关联 -> 独立 transcript 卡片 -> 实时/历史合并 -> 下载鉴权`

不得在无法定位时把卡片永久放到会话末尾，也不得扩大角色、模块、预览、删除、恢复区或他人报告权限。
