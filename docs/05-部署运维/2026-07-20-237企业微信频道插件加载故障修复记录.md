# 237 企业微信频道插件加载故障修复记录

| 项目 | 内容 |
|---|---|
| 事件日期 | 2026-07-20 |
| 影响范围 | 237 上 GAIOP Gateway 的企业微信 Bot 频道；Admin 页面、BFF 配置和 Syslog 接收器未受影响 |

## 1. 现象

企业微信中的 GAIOP 机器人不再回复。Admin BFF 读取到的 `channels.wecom` 仍是已配置、已启用，且凭据字段仍存在；因此这不是页面保存时清空 Bot ID 或 Secret 的问题。

## 2. 根因

企业微信外部插件在故障发现时仍是 `wecom-openclaw-plugin@2026.4.23`。2026-07-16 的多个 Gateway 新进程都能成功加载该插件并完成企业微信长连接认证，说明它并非从 5 月起一直处于“只能靠旧进程维持”的状态。

2026-07-17 10:50，在同一个共享插件目录 `~/.openclaw/npm/node_modules` 中执行钉钉插件安装。钉钉目录创建、插件登记配置写入、Gateway 重启和企业微信首次依赖解析失败在 23 秒内连续发生。结合错误内容，最有证据支持的技术原因是：钉钉插件安装过程改变了共享 npm 依赖树，企业微信插件原有的 `openclaw` peer 依赖解析关系随之丢失或失效；安装动作随后触发 Gateway 重启，新进程立即加载失败。

从 Gateway 日志取得的原始非敏感错误如下：

```text
[plugins] wecom-openclaw-plugin failed to load from /home/netinside/.openclaw/npm/node_modules/@wecom/wecom-openclaw-plugin/dist/index.js: Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'openclaw' imported from /home/netinside/.openclaw/npm/node_modules/@wecom/wecom-openclaw-plugin/dist/src/runtime.js
```

日志证明的直接触发操作是 2026-07-17 的钉钉组件安装及其登记配置写入。它既改动了共享插件安装目录，又要求 Gateway 完整重启；不是企业微信 Bot ID、Secret、企业微信后台访问范围或 BFF 隧道失效。

### 2.1 可验证的故障时间线与触发操作

| 时间（中国标准时间） | 已验证事实 |
|---|---|
| 2026-07-16 16:30:10 | Gateway 日志仍收到企业微信真实消息；同日此前多次记录 `WebSocket connected` 和 `Authentication successful`。 |
| 2026-07-17 10:50:27 | 服务器上钉钉插件目录 `~/.openclaw/npm/node_modules/@dingtalk-real-ai/dingtalk-connector` 创建完成。 |
| 2026-07-17 10:50:35 | Gateway 收到配置变更：`plugins.installs.dingtalk-connector`，日志明确说明该变更“requires gateway restart”。 |
| 2026-07-17 10:50:36 | Gateway 开始完整重启，原企业微信连接被正常关闭。 |
| 2026-07-17 10:50:50 | 重启后的新进程首次记录 `wecom-openclaw-plugin failed to load` 和 `ERR_MODULE_NOT_FOUND`。 |

237 运行账户 `netinside` 的 Shell 历史中存在与上述时间链一致的命令：

```bash
openclaw plugins install @dingtalk-real-ai/dingtalk-connector
```

10:50 的 Gateway 日志没有 `config.patch actor/device` 记录，只表现为外部命令修改配置文件后触发热重载；钉钉插件目录时间、配置变更路径和 Shell 历史命令相互吻合。因此可以确认触发操作是 237 上以 `netinside` 账户执行的钉钉插件安装命令，**不是 Admin BFF 的频道配置接口**。

Shell 历史没有启用时间戳，也没有记录 SSH 来源 IP 或实际人员身份；现有认证日志不足以把该运行账户对应到某个人。因此只能归属到服务器账户 `netinside`，不能可靠指认具体操作者。此前把 11:45 的另一条 BFF 飞书配置审计误套到 10:50 钉钉安装事件上，是错误关联，现已删除。

`openclaw@2026.5.4` 的当前安装目录时间为 2026-05-06，但这只能说明该版本当时已安装；它不是本次 7 月故障的触发操作。此前将本次故障表述为“Gateway 升级导致”是不正确的，现已更正。

故障时段的系统日志未出现 `ENOSPC`、磁盘满、I/O 错误、写入失败、OOM、进程被内核杀死、`EACCES` 或权限拒绝；服务器自 2026-03-07 起也未重启。当前根文件系统使用率 48%、inode 使用率 10%。因此没有证据支持磁盘损坏、容量耗尽、OOM、意外重启或权限变更是本次诱因。由于服务器未保留当次 npm 调试日志和安装前依赖树快照，无法进一步还原 npm 在内部具体删除或重排了哪个链接；本文不把该内部动作写成百分之百已审计事实。

另见独立的飞书“plugin not installed”警告；本次没有处理飞书，以免扩大企业微信故障修复范围。

## 3. 诊断过程与命令

以下命令在 237 的 GAIOP 运行账户下执行；SSH 登录凭据由本机安全存储提供，未写入命令、日志或本文档。

### 3.1 确认插件、频道和 Gateway 当前状态

```bash
# 确认运行时加载状态
export PATH="$HOME/.npm-global/bin:$PATH"
openclaw plugins inspect wecom-openclaw-plugin --runtime
# 当前版本也接受 npm 包名：
openclaw plugins inspect @wecom/wecom-openclaw-plugin --runtime

# 先进行不改动状态的更新预演
openclaw plugins update wecom-openclaw-plugin --dry-run

# 查询实际频道运行状态
openclaw channels status

# 查询 Gateway 服务、RPC 探针和监听状态
openclaw gateway status --deep --require-rpc
```

故障时 `inspect --runtime` 返回 `Status: error`、`Failure phase: load` 和 `ERR_MODULE_NOT_FOUND`；Gateway 本身可达，`channels.wecom` 仍已配置。更新预演及实际 `plugins update` 均认为旧插件“up to date”，不能修复依赖解析关系，因此需要按企业微信官方安装器重新安装。

### 3.2 定位最后正常、首次失败与触发事件

```bash
# 提取故障窗口；过滤条件避免输出消息正文、response_url 和频道凭据
journalctl --user-unit openclaw-gateway.service \
  --since '2026-07-17 10:48:00' \
  --until '2026-07-17 10:52:30' \
  --no-pager |
grep -Ei 'config change|requires gateway restart|starting channels|wecom-openclaw-plugin failed to load|ERR_MODULE_NOT_FOUND|\[wecom\].*(Disconnect|Authentication successful|WebSocket connected)'

# 查找历史上第一次相同加载错误
journalctl --user-unit openclaw-gateway.service \
  --since '2026-07-01 00:00:00' --no-pager |
grep -F 'wecom-openclaw-plugin failed to load' | head

# 证明故障前企业微信新进程仍可建立连接
journalctl --user-unit openclaw-gateway.service \
  --since '2026-07-14 00:00:00' \
  --until '2026-07-17 10:50:35' --no-pager |
grep -E '\[wecom\].*(WebSocket connected|Authentication successful|Authenticated)' | tail -n 30

# 核对钉钉插件目录创建时间
stat -c '%y %z %n' \
  /home/netinside/.openclaw/npm/node_modules/@dingtalk-real-ai/dingtalk-connector

# 只查找目标安装命令，不输出不相关的 Shell 历史
grep -nF 'openclaw plugins install @dingtalk-real-ai/dingtalk-connector' \
  /home/netinside/.bash_history
```

以上查询得到的关键对应关系是：钉钉目录创建于 10:50:27，Gateway 在 10:50:35 检测到 `plugins.installs.dingtalk-connector`，10:50:36 重启，企业微信在 10:50:50 首次加载失败。

### 3.3 排除服务器重启、磁盘、OOM、I/O 与权限异常

```bash
# 系统重启历史
last reboot -F | head

# 故障窗口内的系统级异常
journalctl \
  --since '2026-07-17 10:40:00' \
  --until '2026-07-17 11:00:00' \

grep -Ei 'ENOSPC|no space left|disk full|I/O error|write failed|out of memory|oom-kill|killed process|EACCES|permission denied|segfault'

# 当前容量和 inode 状态，仅作为补充，不能代替历史监控

```

查询结果：故障窗口没有匹配的系统异常；服务器自 2026-03-07 起未重启；检查时根文件系统使用率 48%、inode 使用率 10%。

### 3.4 当前版本支持的日志命令

237 的 `openclaw logs --help` 证明当前版本支持 `--follow`、`--plain`、`--local-time`、`--limit` 等参数，不支持 `--level`、`--filter` 或 `--dump`。可使用：

```bash
# 实时跟踪；使用 Ctrl+C 结束
openclaw logs --follow --plain --local-time |
grep --line-buffered -Ei 'wecom|ERR_MODULE_NOT_FOUND'

# 查询当前 Gateway 日志窗口
openclaw logs --plain --local-time --limit 2000 |
grep -Ei 'wecom|ERR_MODULE_NOT_FOUND'
```

跨进程、跨日期回溯仍以 `journalctl --user-unit openclaw-gateway.service` 为准。`ERR_MODULE_NOT_FOUND` 只能直接证明模块解析失败，不能仅凭这一行断言磁盘文件损坏。

## 4. 修复过程与命令

### 4.1 保护现有配置

在执行强制安装前，先在服务器受保护目录 `~/.openclaw/backups/` 创建了 `openclaw.json` 备份。备份中可能含频道凭据，未下载、未展示、未写入 Git 或本文档。

本次实操已产生下述受保护备份；后续复现时应使用以下标准化等价命令：

```bash
install -d -m 700 /home/netinside/.openclaw/backups
install -m 600 \
  /home/netinside/.openclaw/openclaw.json \
  /home/netinside/.openclaw/backups/gaiop-wecom-before-reinstall-20260720T014016Z.json
```

备份文件只保留在 237 的受保护目录，不能直接打印或复制到开发文档。

### 4.2 首次失败及原因

首次执行官方安装器：

```bash
npx -y @wecom/wecom-openclaw-cli install --force --skip-config
```

失败日志：

```text
/bin/sh: 1: openclaw: not found
```

原因是非交互式服务环境的 `PATH` 未包含 `$HOME/.npm-global/bin`。该安装器的 `--force` 会先清理旧插件/配置再安装，所以此次失败后立即使用前述受保护备份做了恢复准备；这是 ISO 部署脚本必须规避的风险点。

### 4.3 成功重装与最小配置恢复

使用正确的运行时路径重新执行：

```bash
export PATH="$HOME/.npm-global/bin:$PATH"
npx -y @wecom/wecom-openclaw-cli install --force --skip-config
```

关键成功输出：

```text
Installed @wecom/wecom-openclaw-plugin@latest
Linked peerDependency "openclaw" -> /home/netinside/.npm-global/lib/node_modules/openclaw
Restarted systemd service: openclaw-gateway.service
```

安装器未自动恢复原有 `channels.wecom`，因此仅从受保护备份恢复该对象（`botId`、`secret`、启用状态及运行选项），没有恢复或改动任何其他频道配置。恢复采用临时文件原子替换后重启 Gateway；本次恢复逻辑等价于：

```bash
# 只恢复 channels.wecom；脚本不输出配置值
node <<'NODE'
const fs = require('fs')
const configPath = '/home/netinside/.openclaw/openclaw.json'
const backupPath = '/home/netinside/.openclaw/backups/gaiop-wecom-before-reinstall-20260720T014016Z.json'
const temporaryPath = `${configPath}.gaiop-wecom-restore.tmp`
const current = JSON.parse(fs.readFileSync(configPath, 'utf8'))
const backup = JSON.parse(fs.readFileSync(backupPath, 'utf8'))

if (!backup.channels?.wecom) {
  throw new Error('protected backup does not contain channels.wecom')
}

current.channels ||= {}
current.channels.wecom = backup.channels.wecom
fs.writeFileSync(temporaryPath, `${JSON.stringify(current, null, 2)}\n`, {
  encoding: 'utf8',
  mode: 0o600,
})
fs.renameSync(temporaryPath, configPath)
console.log('channels.wecom restored from protected backup')
NODE

export PATH="$HOME/.npm-global/bin:$PATH"
openclaw gateway restart
```

凭据值、Bot ID 和完整配置内容均未输出。

## 6. 后续预防与验收

1. ISO 构建时冻结 Gateway 与企业微信插件的兼容版本，并在镜像验收中执行一次 `plugins inspect --runtime` 和 `channels status`。
2. 部署/维护脚本必须显式提供运行时 `PATH`，不能依赖交互式 shell；否则官方重装器可能找不到 `openclaw`。
3. 强制重装前必须创建受保护配置备份，并只恢复确认需要的频道对象；不得把备份复制到开发机、文档或仓库。
4. Admin 频道页后续应区分“已配置/已启用”和“插件加载失败/频道未运行”，避免配置存在时误判为可用。
5. 2026-07-20 用户已确认企业微信真实消息可正常回复；私聊/群聊覆盖、断网重连、Gateway 冷启动恢复和会话隔离仍纳入最终集中验收。
