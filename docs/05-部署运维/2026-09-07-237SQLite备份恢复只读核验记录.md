# 2026-09-07 237 SQLite 备份恢复只读核验记录

## 结论

本次没有执行生产恢复、删除、部署、重启或配置写入。Admin 与 Upgrade 的备份 timer 均为 `active/enabled`，最近一次 one-shot 回执为 `success`（退出码 `0`），两个生产数据库的 `quick_check` 与 `integrity_check` 均为 `ok`。

但两个受控 SQLite 备份根均没有符合当前策略的有效日、周或月备份对，因此不能完成“最新备份复制件”的恢复演练：日/周/月有效文件数和容量均为零，恢复状态为 `not_run/no_valid_backup`。这不是数据库损坏证据，而是备份创建开关目前为关闭态的直接结果。旧条目即使存在，也没有被当作受控备份使用或删除。

## 本次新增只读验证入口

在 Admin 仓库执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Invoke-237SqliteBackupRecoveryVerify.ps1
```

该入口只使用本机已有的加密连接记录，且固定执行下列检查：

- Admin、Upgrade timer 的 active/enabled、最近触发时间，以及最后 service 回执；
- 两个生产数据库的只读 `quick_check`/`integrity_check`；
- 受控备份根的权限、日/周/月有效 manifest+SHA-256+完整性统计、最新周期和容量；
- 创建与清理开关的布尔投影，不输出环境文件或秘密；
- 若存在有效备份，仅使用最新一份的 SQLite API 复制件，在既有 `sqlite-restore-tests` 目录中校验完整性与关键表的存在/列数；临时 `.sqlite3`、WAL、SHM 均在结束时删除。

入口不接受路径、命令、生产库目标、删除或部署参数。它不读取业务行、凭据或原始日志。

## 当前受阻项与后续受控步骤

本次实时核验时，两个组件的创建开关和清理开关都为 `false`。旧备份自动删除保持关闭，未作改动。根目录中存在不满足当前 manifest 命名和配对策略的历史条目；它们不能安全地作为恢复源，也不能被本机制删除。

新创建机制使用各自 `sqlite-backups/v1` 子目录。这样保留历史根目录条目不动，同时让当前策略只管理严格命名的三层备份与 manifest；`v1` 目录由受控发布创建为组件专属 `0700`，不会扫描、迁移、覆盖或清理父目录内容。

要形成首个可恢复证据，需要另行批准一个受控的“仅启用创建、清理保持 false”的发布/配置步骤。执行前必须先完成 Upgrade 活动目录与待部署源码的文件级差异核验；当前活动 Upgrade 源码无法由本地已提交版本直接对应，不能为了启用开关覆盖它。完成该前置核验后，应等待/触发一次受控备份，再重新运行本入口，确认三个层级均有有效 manifest 对，并验证最新副本恢复。

## 验收边界

- 不把 timer 的 `success` 当作已生成备份的替代证据；
- 不把历史、未命名或 manifest 不匹配的条目当作可恢复备份；
- 不启用旧备份自动删除，不清理任何备份；
- 生产灾难恢复仍须单独批准停机窗口、当前库保护、目标校验和回滚方案。
