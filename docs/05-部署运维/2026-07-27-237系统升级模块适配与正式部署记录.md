## 1. 为什么需要适配

同事已经在 `GAIOP-upgrade` 仓库完成升级成功后删除上传包等后端改动，237 也运行着该版本的旧部署，但它还不能直接作为 GAIOP 正式升级链路使用。

只读预检确认：

1. 旧 `napm-upgrade.service` 以 `netinside` 运行并监听 18900，但非健康接口没有生产鉴权，未鉴权读取状态仍返回 200。
2. Admin 没有配置升级服务地址和内部 Token，页面与升级服务没有真正接通。
3. 旧前端目标是 `/var/www/napm-admin`，237 实际前端位于 `/opt/gaiop/admin/dist`。
4. 前端目标不能指向 `/opt/gaiop/admin`，否则会连 BFF、服务器代码和运行文件一起替换，必须精确到独立 `dist`。
5. OpenClaw 升级器原先使用系统级 `systemctl restart openclaw`，237 实际运行的是 `netinside` 用户级 `openclaw-gateway.service`。
6. 升级服务需要同时管理 `gaiop` 所有的 Admin 前端和 `netinside` 所有的 OpenClaw、插件及 Skills，单一普通用户无法在不扩大目录权限的前提下完成跨所有者原子替换。
7. ZIP 校验缺少路径穿越、重复条目、类型外文件和组件名称路径片段等约束。
8. 测试依赖仓库中的测试私钥及共享数据库实例，存在环境耦合和 SQLite `BUSY` 风险。
9. 页面仍提示回滚和备份删除“尚未开放”，与实际 BFF 能力不一致。

本次不是重写 OpenClaw，也不是把升级元数据塞进 Gateway，而是在 GAIOP Admin BFF 后面建立独立、受控、可鉴权、可回滚的升级服务。

## 2. 最终链路与边界

```text
浏览器
  -> GAIOP Admin BFF（管理员认证、确认口令、审计、响应脱敏）
  -> 内部 Token + 当前管理员身份
  -> 127.0.0.1:18900 gaiop-upgrade.service
  -> 签名/清单/版本/ZIP 安全校验
  -> 备份 -> 组件替换 -> 专用重载与健康检查
  -> 成功后清理上传包；失败时自动回滚
```

- 浏览器不知道升级服务地址、内部 Token、安装路径和备份路径。
- Gateway/OpenClaw 不承载 Admin 会话、升级来源或升级控制数据。
- 升级服务只监听回环地址，不对公网开放 18900。
- `/health` 供本机探针访问；其他接口必须携带内部 Token 和操作者身份。
- 本次没有修改 OpenClaw 源码、频道插件业务代码、报告文件管理或会话管理。

旧数据库和备份的迁移方式：

- 停止旧服务后执行 SQLite WAL checkpoint，再复制数据库；
- 旧备份内容复制到新备份根；
- `components.install_path` 修正为 237 实际路径；
- 数据库中 `/var/backups/napm/...` 记录映射到新备份根；
- 原旧服务代码和备份纳入部署级备份，不以删除旧目录作为发布前提。

## 4. 升级后端修改

### 4.1 生产鉴权

新增 `src/runtime-safety.js`：

- `NODE_ENV=production` 时强制要求 `GAIOP_UPGRADE_INTERNAL_TOKEN`；
- 缺少 Token 时拒绝启动，不能静默降级为无鉴权；
- 服务默认绑定 `127.0.0.1`。

除 `/health` 外：

- 缺少或错误 Token 返回 401；
- 使用定长安全比较；
- 缺少操作者身份返回 400；
- BFF 传入当前管理员名称，升级服务独立审计。

### 4.2 ZIP 与组件校验

`UpgradeValidator` 增加：

- 拒绝绝对路径、`..` 路径穿越和不安全条目；
- 拒绝重复条目；
- 拒绝清单未声明的类型外文件；
- 固定核心组件名称；
- 组件标识只能使用安全字符，不能携带目录片段；
- 单 Skill 包目录必须与清单声明组件一致。

这些约束保证解包和替换只能落入预期组件目录。

### 4.3 Admin 前端适配

`FrontendUpgrader`：

- 默认目标改为 `/opt/gaiop/admin/dist`；
- 目标最后一级必须是 `dist`，防止覆盖 Admin BFF；
- 健康检查使用 `http://127.0.0.1:3000/api/health`；
- 完成后恢复 `gaiop:gaiop`，目录 0755、文件 0644。

### 4.4 OpenClaw 与 Skills 适配

`OpenClawUpgrader` 不再拼接系统级 `systemctl`，改为调用固定辅助程序：

`/usr/local/libexec/gaiop-upgrade-restart-openclaw`

辅助程序只允许：

- `--check`：检查 `netinside` 用户级 Gateway 是否 active；
- 无参数：重启固定的 `openclaw-gateway.service`。

它不接受任意服务名或命令。OpenClaw、插件、Bundle 和单 Skill 替换后统一恢复 `netinside:netinside`。

### 4.5 成功包清理与测试

- 只有最终状态为 `success` 才删除上传包；
- 失败、回滚和异常任务保留包供排查；
- 新增独立 `PackageCleaner` 和测试；
- `UpgradeEngine` 支持注入测试数据库，避免共享 SQLite 锁；
- 测试动态生成临时 RSA 密钥对，不再依赖仓库私钥；
- 增加生产 Token、包清理、ZIP 路径和组件布局测试。

## 5. systemd 权限模型

`gaiop-upgrade.service` 以 root 启动，是因为它需要原子替换两个不同所有者的目录：

- `gaiop`：Admin `dist`；
- `netinside`：OpenClaw、插件和 Skills。

如果改成单一普通用户，只能通过放宽 ACL 或让一个业务账户控制另一个账户目录实现，权限边界反而更差。

root 服务同时受到以下限制：

- `NoNewPrivileges=true`；
- `ProtectSystem=strict`、`ProtectHome=read-only`；
- `PrivateTmp`、`PrivateDevices`；
- 内核、控制组、实时调度和 SUID/SGID 保护；
- `RuntimeDirectory=gaiop-upgrade`；
- `ReadWritePaths` 只列出状态、备份、Admin、OpenClaw、Skills、插件和用户级 systemd 运行目录。

此外仍有回环监听、BFF Token、签名与 ZIP 校验、固定目标路径四层约束。

## 6. Admin BFF 和页面修改

- 浏览器只访问 BFF，BFF 注入内部 Token 和当前管理员；
- 执行、Skill 回滚和删除分别要求 `EXECUTE`、`ROLLBACK`、`DELETE`；
- 返回浏览器的数据不含服务器路径或内部配置；
- `pending` 任务也自动轮询；
- 页面说明修正为升级、Skill 回滚和备份删除均通过 Admin BFF；
- 明确当前人工回滚只支持 Skill。

## 7. 受控部署过程

### 7.1 预检和隔离验证

部署前确认 Ubuntu 22.04、x86_64、Node `v22.14.0`、Admin/Gateway/旧升级服务健康、真实目录和所有者、约 50GB 可用空间及 Admin 尚未接入升级服务。

候选包先在 237 `/tmp` 隔离目录中：

1. 校验 SHA-256；
2. 解包；
3. 使用服务器 Node 22 安装生产依赖；
4. 运行完整测试；
5. 删除临时目录和候选包。

结果为 66/66 通过。

### 7.2 正式切换顺序

1. 校验服务包和 Admin `dist` 包哈希；
2. 临时目录再次安装并测试；
3. 备份旧服务、unit、Admin 环境文件和 `dist`；
4. 停止并禁用旧服务；
5. 安装新服务、systemd unit 和固定 Gateway 辅助程序；
6. 迁移数据库、组件路径和备份记录；
7. 在服务器生成随机内部 Token，只写配置、不输出；
8. 给 Admin 配置相同 Token 和回环服务地址；
9. 安装新 Admin `dist`；
10. 启动新服务并重启 Admin；
11. 验证状态、鉴权、健康、辅助程序、前端树哈希和页面文字。

### 7.3 失败、原因和回滚

过程中的失败也保留记录：

1. 临时阶段曾以 root 运行升级测试，与已验证的 `netinside` 环境不一致。此时尚未改变生产，脚本退出；后改为统一以 `netinside` 运行。
2. 第一次生产切换时升级服务正常，但 Admin 启动失败。原因是 `/etc/gaiop/admin.env` 被设置为 `root:root 0600`，而 Admin 由 `gaiop` 用户直接读取该文件。
3. 自动回滚恢复了旧 Admin、旧升级服务和原配置。
4. Admin 环境文件修正为 `root:gaiop 0640` 后重发成功；升级服务自己的环境文件仍为 `root:root 0600`。

没有绕过失败继续部署。生产阶段的这次失败实际验证了自动回滚链路。
