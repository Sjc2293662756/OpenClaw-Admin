## 1. 问题与生产基线

仪表盘首次进入和切换统计范围时等待明显。237 只读核查确认 Admin BFF、Gateway 和主机资源均正常，瓶颈不是服务异常，而是仪表盘直接等待 `sessions.usage` 的全量结果：

| 范围 | 修改前生产耗时 | 响应大小 | 会话数 |
|---|---:|---:|---:|
| 最近 7 日 | 2472 ms | 184200 B | 78 |
| 最近 30 日 | 6306 ms | 647983 B | 277 |
| 最近 90 日 | 6514 ms | 688794 B | 289 |

同时发起两个相同统计请求时，两者均约 13 秒完成，说明上游统计会相互争用，页面重复触发会进一步放大等待。

## 2. 根因

1. 页面在 WebSocket 尚未连接时先执行一次完整刷新，首次连接后又执行一次，存在重复统计机会。
2. 仪表盘直接调用 Gateway `sessions.usage`，缺少面向页面的单航班合并和短时缓存。
3. Gateway 返回的每会话明细远超仪表盘展示需要，30 至 90 日响应达到约 0.6 至 0.7 MB。
4. 连续切换时间范围时，请求可并行争用；旧请求虽有结果代次保护，但仍消耗上游计算。

## 3. 修改内容

### 3.1 Admin BFF

- 新增鉴权接口 `GET /api/dashboard/usage`，只允许登录用户访问。
- BFF 内部仍调用既有 `sessions.usage`，未修改 OpenClaw 或 GAIOP 后端。
- 按用户身份、开始日期和结束日期隔离 30 秒内存缓存，最多保留 64 项。
- 同一用户、同一时间范围的并发请求只执行一次上游统计，其余请求共享结果。
- 只投影仪表盘实际需要的总量、模型、供应商、工具、消息、趋势和会话覆盖字段，移除大体积会话明细。
- 手动刷新使用 `force=1` 绕过已完成缓存，但仍共享正在执行的同条件请求。

### 3.2 前端

- 在状态订阅建立且服务端时间同步完成后，只在 Gateway 已连接时执行一次首屏刷新。
- 首次连接事件只补发一次，不再在未连接阶段提前发起失败或重复统计。
- 使用“单活动任务 + 仅保留最新待处理范围”的执行器串行统计请求；快速切换范围时丢弃中间待处理范围。
- 旧范围结果不能覆盖用户最新选择。
- 手动刷新和失败重试明确走强制刷新。
